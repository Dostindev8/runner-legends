```
├── Requisitos:          Node.js 22+ · FFmpeg
├── Router:             /hyperframes → mapea "hazme un video/deck" al workflow correcto

│                        · figma (import de diseño)
```

#### 🦾 Protocolo de Mecatrónica / Robótica Avanzada / Exoesqueletos

Cuando el pedido es "construir un robot", "un exoesqueleto", "una armadura", "un brazo
robótico" o similar — **es un proyecto de ingeniería mecatrónica real**, no una fantasía.
Se descompone igual que cualquier sistema crítico: primeros principios, capas, verificación.

```
┌─────────────────────────────────────────────────────────────────────┐
│  CAPA 1 — ESTRUCTURA Y MATERIALES                                    │
│  ├── CAD paramétrico: Fusion 360 / SolidWorks / FreeCAD              │
│  ├── Selección de material por relación resistencia/peso: aluminio   │
│  │   6061-T6, fibra de carbono, PLA/PETG-CF para prototipo rápido    │
│  ├── FEA (análisis de elementos finitos) antes de fabricar: cargas,  │
│  │   fatiga, factor de seguridad ≥2x en puntos de esfuerzo           │
│  └── Fabricación: impresión 3D (prototipo) → CNC/fibra (producción)  │
├─────────────────────────────────────────────────────────────────────┤
│  CAPA 2 — ACTUACIÓN Y POTENCIA                                       │
│  ├── Actuadores: servos brushless + encoder, motores paso a paso,    │
│  │   actuadores lineales, o músculos neumáticos según fuerza/peso    │
│  ├── Control de motor: FOC (Field-Oriented Control) para precisión   │
│  ├── Presupuesto de potencia: torque requerido × margen de seguridad,│
│  │   autonomía de batería (Wh) vs. peso, gestión térmica             │
│  └── Transmisión: reductores planetarios/harmonic drive según backlash tolerable │
├─────────────────────────────────────────────────────────────────────┤
│  CAPA 3 — SENSORES Y PERCEPCIÓN                                      │
│  ├── IMU (9-DoF) + encoders de posición en cada articulación         │
│  ├── Sensores de fuerza/torque (para exoesqueletos: EMG opcional     │
│  │   para intención de movimiento del usuario)                       │
│  ├── Sensor fusion: EKF/UKF combinando IMU + encoders + visión       │
│  └── Visión (si aplica): cámara + SLAM o detección de objetos edge   │
├─────────────────────────────────────────────────────────────────────┤
│  CAPA 4 — CONTROL Y FIRMWARE                                         │
│  ├── Firmware de bajo nivel: C/C++ sobre STM32/ESP32 · FreeRTOS      │
│  │   para loops de control determinísticos (ej. 1kHz para exo)       │
│  ├── Control: PID por articulación → MPC para movimiento coordinado  │
│  ├── Capa media: ROS2 (nodos de control, tf2 para cinemática)        │
│  └── Cinemática: directa/inversa por DH parameters o solvers (KDL,   │
│      MoveIt2 para manipuladores)                                     │
├─────────────────────────────────────────────────────────────────────┤
│  CAPA 5 — SEGURIDAD FÍSICA (NO NEGOCIABLE, especialmente wearables)  │
│  ├── Límites de torque/velocidad por software Y por hardware (fusible│
│  │   mecánico/embrague de seguridad — nunca solo límite en software) │
│  ├── Botón de parada de emergencia físico, siempre accesible         │
│  ├── Watchdog timer: si el loop de control falla, ir a estado seguro │
│  ├── Para exoesqueletos: límites de rango articular por debajo del   │
│  │   límite biomecánico humano, detección de resistencia anómala     │
│  └── Testing HIL (Hardware-in-the-Loop) antes de cualquier prueba    │
│      con carga o con humano                                          │
└─────────────────────────────────────────────────────────────────────┘
```

**Regla de honestidad de alcance:** un "traje volador con propulsión de repulsores" no existe

## 🛡️ GATE DE CALIDAD — objetivo cero defectos (no garantía)

Antes de decir “sin errores / todo funcionando”:

```
□ El cambio hace exactamente lo pedido — nada más
□ Build de producción pasa (o se reporta el error real)
□ No se rompió contenido de negocio (copy, precios, NCF, intro, WhatsApp)
□ No hay secretos en git ni en el bundle
□ Enlaces externos: rel="noopener noreferrer"
□ Mobile 375px no recorta logos (object-contain)
□ Si hay 3D/video: lazy + no bloquear el resto del sitio
□ Declarar lo que NO se pudo verificar (dominio custom, DNS, cert)
□ ISO 25010: característica(s) de calidad impactada(s) nombrada(s)
□ ISO 12207: requisito → diseño → código → prueba trazable en 1 línea
□ ISO 29119: técnica de prueba usada declarada (si aplica testing)
□ ISO 27001: si hay datos sensibles, riesgo evaluado antes de implementar
□ NIST SSDF: práctica PO/PS/PW/RV relevante identificada
□ CMMI: nivel de proceso adecuado al tamaño/criticidad
□ OWASP Top 10 + DevSecOps: sin regresión de seguridad conocida
```

Taxonomía de error al reportar:
```
FALLO DE BUILD     → pegar el error, no parafrasear
FALLO DE RUNTIME   → repro steps + hipótesis de 1 línea
FALLO DE INFRA     → Vercel Ready ≠ dominio custom resuelve
FALLO DE ALCANCE   → el usuario pidió X; Y quedó fuera (decirlo)
FALLO DE CALIDAD   → no pasa Quality Gate normativo (ISO/NIST/CMMI)
```

### 1. Anatomía obligatoria de un `SKILL.md`

```
├── description = CONDICIÓN de activación, no resumen. Patrón: "Use this skill when the
│   user wants to X / mentions Y / needs Z" — es lo único que el agente lee para decidir
│   si se auto-invoca. Una descripción vaga = skill que nunca dispara o dispara siempre.
├── Protocolo de ejecución completo, paso a paso, sin ambigüedad
├── (si el skill genera sub-skills o outputs) templates/ con la forma exacta de salida
└── README.md aparte, legible por humano: problema que resuelve + 3 "suggested prompts"
    de ejemplo + cómo funciona (esto NO reemplaza al SKILL.md, es la ficha de presentación)
```

### 2. Metodología RIA-TV++ — destilar CUALQUIER contenido en un skill ejecutable

Úsala cuando la tarea es "convierte este libro/video/transcripción/documentación en un
skill", incluida la destilación de tus propios super prompts `/god-stack-ing` en módulos
reutilizables. 7 etapas, sin saltar ninguna:

```
1. COMPRENSIÓN GLOBAL (método Adler)
   estructura → interpretación → crítica → aplicación → produce un OVERVIEW.md

2. EXTRACCIÓN PARALELA — 5 lentes sobre el mismo material
   frameworks · principios · casos reales · contraejemplos · terminología propia

3. TRIPLE VERIFICACIÓN — filtro de calidad, NO aceptar todo
   Cada candidato a "skill" debe pasar los 3 tests, o se descarta:
   ① ≥2 evidencias independientes cruzadas dentro del material original
   ② Poder predictivo: responde preguntas NUEVAS no explícitas en el contenido
   ③ No-trivialidad: no es sentido común / conocimiento ya obvio
   Tasa de aprobación esperada: 25-50%. Si aprueba >70%, el filtro está flojo.

4. CONSTRUCCIÓN RIA++ — cada unidad aprobada en 6 dimensiones
   R  cita textual original (mínima, solo ancla)
   I  reescritura con palabras propias
   A1 caso de ejemplo tomado del material original
   A2 escenario futuro de aplicación (proyección)
   E  pasos ejecutables concretos
   B  límites y puntos ciegos — dónde NO aplica

5. ENLACE ZETTELKASTEN
   mapear dependencias/combinaciones entre las unidades → INDEX.md con grafo de referencias

6. STRESS TEST — antes de dar el skill por terminado
   diseñar preguntas trampa + casos de confusión cruzada con otros skills existentes
   (ej.: ¿se confunde con `finance-brand-strategist` o `supreme-engineer-omega-absolute`?)
```

### 3. Jerarquía de 3 capas — cuándo un dominio se vuelve suite

```
Skill    → conocimiento/framework para UNA tarea. Se activa AUTOMÁTICO por descripción.
Command  → workflow manual (/nombre-comando) que ENCADENA varios skills en secuencia.
Plugin   → paquete instalable que agrupa skills + commands de un mismo dominio.
```

número de skills relacionados crece y empiezan a pisarse o a necesitar orquestación
explícita (patrón visto en `pm-skills`: 68 skills + 42 commands agrupados en 9 plugins).
